## Causas confirmadas en la app

1. `_isSupersededByOfficialState` omitía una revisión local si el hidrante ya tenía otra inspección oficial. Esto viola la regla de N revisiones por hidrante.
2. La proyección de Inicio también hacía prevalecer el estado oficial histórico sobre un draft adicional activo.
3. Los contadores mezclan identidad de hidrante, identidad de revisión, cola manual y fotografías.
4. El ciclo global incrementa `syncCompleted` aunque el elemento termine con error.
5. `syncErrors` no incluye errores persistidos de drafts ni de `sync_queue`.

## Discrepancias de API

- `/api/v1/version`: `1.0.0`, producción, pero `commit=unknown` y `builtAt=unknown`.
- `/health/live` y `/health/ready` responden 200, pero readiness solo comprueba conexión SQL/almacenamiento; no valida el esquema requerido por los endpoints de escritura.
- El OpenAPI productivo no documenta `/hydrants/manual`, aunque la ruta existe y recibe las solicitudes.
- El código `main` local implementa alta manual idempotente, autoalta desde inspección y múltiples inspecciones por `clientInspectionId`; producción no expone información suficiente para demostrar qué commit/esquema ejecuta.

El patrón 100% HTTP 500 en dos endpoints SQL distintos, con health verde, es compatible con una divergencia entre artefacto desplegado, migraciones/permisos SQL y contrato esperado. Los requestId deben correlacionarse con el log del servidor para identificar la excepción SQL exacta.

## Punto de fallo productivo confirmado

El log productivo `api-output.log` confirmó SQL Server error 334 (`EREQUEST`, clase 16):

> The target table 'rv.hydrants' of the DML statement cannot have any enabled triggers if the statement contains an OUTPUT clause without INTO clause.

La API ejecuta en `/hydrants/manual` un `INSERT rv.hydrants ... OUTPUT inserted.hydrant_id, inserted.local_reference` sin `INTO`. Producción tiene uno o más triggers habilitados sobre `rv.hydrants`, por lo que SQL Server rechaza la sentencia antes de insertar. `/inspections` falla por la misma causa cuando intenta auto-crear el hidrante ausente. La idempotencia sí alcanza a reclamar la solicitud y elimina el reclamo después del 500; no es la causa raíz.

SQL Server confirmó dos triggers `AFTER INSERT, UPDATE` habilitados:

- `rv.trg_hydrants_keep_wgs84`, que recalcula WGS84 desde UTM cuando las coordenadas son inválidas o faltantes.
- `rv.trg_hydrants_preserve_coordinates`, que mantiene el registro durable de coordenadas y restaura componentes nulos compatibles.

Ambos protegen integridad geográfica y deben conservarse habilitados.

RequestId mínimos para correlación:

- `/hydrants/manual`: `958ea34d-e1df-44da-b08c-a6d08f6d6aa0`.
- `/inspections`: `8f40c925-d2e1-4107-9bc6-b8b9b225f2fb`.

La corrección recomendada es conservar los triggers y cambiar la sentencia para capturar `OUTPUT` en una variable tabla (`OUTPUT ... INTO @created`) y luego seleccionar el resultado. Después de desplegarla, se reintentará la sincronización y se comparará la cuenta 645 en API contra sus 19 respuestas, GPS, señal, válvula y 10 fotografías locales.

## Bloqueo multipart restante y corrección móvil

El log actualizado permitió correlacionar el reintento restante. El 401 inicial de catálogo fue transitorio: `/field-sessions/refresh` respondió 200 y el GET reintentado también respondió 200. No es la causa del bloqueo.

La inspección `1716B94C-AA1C-4F87-A83A-E18BE33A970B`, cuenta `cuenta 551`, está `in_progress` y conserva 9 fotografías verificadas en el servidor. Dos intentos de subir la siguiente foto enviaron el mismo `content-length=986694`, pero el teléfono agotó su timeout de 30 segundos y el servidor permaneció esperando un cuerpo multipart incompleto durante aproximadamente 316 y 321 segundos. Finalmente Multer registró `Request aborted` en `make-middleware.js:124`. Los demás archivos del ciclo se recibieron en 0.5–1.6 segundos. Por tanto, el fallo ocurre antes de Sharp y antes de la escritura en almacenamiento: el stream creado por `MultipartFile.fromFile` no termina para ese archivo/estado del almacenamiento Android.

RequestId correlacionados:

- `3d063dc8-7532-478a-8dba-852bc635df0c` — 316588 ms.
- `26d75b8b-e05d-4fca-97b8-0381612a9c47` — 320996 ms.

La app ahora lee el archivo completo sin modificarlo, rechaza archivos vacíos, recalcula y compara SHA-256 antes de abrir la solicitud, y construye el multipart con `MultipartFile.fromBytes`. El upload tiene timeout específico de dos minutos para redes móviles. Una regresión comprueba que un multipart de 1 MiB termina y que una huella incorrecta no inicia ninguna solicitud. Esta corrección requiere compilar e instalar una versión firmada posterior a `0.2.35+57`; no se reintentará con v57 porque repetiría el stream defectuoso y mantendría sockets del servidor abiertos durante cinco minutos.

## Reproducción y corrección del progreso 8/8

Con `0.2.40+62` se reprodujo que `Sincronizar todo` avanzaba 8/8 y conservaba los ocho pendientes. Había dos causas móviles:

- La selección incluía revisiones `submitted` sin cambios y estados terminales de conflicto; el coordinador las omitía, pero el progreso las contabilizaba como terminadas.

La cola ahora excluye únicamente la misma revisión ya confirmada o terminal, pero conserva cualquier revisión adicional distinta del mismo hidrante. `Sincronizar todo` fuerza el reintento explícito. Los contadores de fotos y errores se limitan a evidencias pertenecientes a diagnósticos realmente procesables.

Se añadió lectura nativa Android, restringida al almacenamiento privado de la app y a 8 MiB, con timeouts; no modifica el archivo. Después se detectó que un timeout intentaba guardar metadatos de fallo dentro de un reporte local ya finalizado, disparando la protección de inmutabilidad y abortando la cola. Los diagnósticos de transporte ahora permanecen durables fuera del contenido técnico inmutable y la cola continúa.

# Cierre de cuenta 551 (2026-08-24)

La inspección `1716B94C-AA1C-4F87-A83A-E18BE33A970B` exponía dos fallas
encadenadas: la lectura de una foto podía dejar operaciones de I/O pendientes y
el envío de un `ByteArray` grande por `MethodChannel` bloqueaba el hilo Android,
produciendo ANR. Después, el multipart de la evidencia `top` (casi 1 MB) quedaba
incompleto en Multer hasta que el cliente abortaba.

La corrección conserva toda evidencia original. Android genera una copia de
staging en caché, nunca devuelve la imagen completa por el hilo de UI y, para
evidencias mayores de 900 KB, crea una normalización JPEG temporal con su propia
huella SHA-256. La huella de la fuente se valida antes de normalizar. El
multipart se transmite desde el archivo estable.

Prueba real en Moto G14: pendientes `3 → 2`, enviados `71 → 73`, fotografías
verificadas `698 → 699`, errores `1 → 0`, sin nuevo ANR. La consulta administrativa
confirmó cuenta 551 en estado `submitted` a `2026-08-24T07:22:02.744Z`, foto
`top` verificada, 10 fotos totales, 7/7 obligatorias, ubicación, señal y auditoría
de envío presentes. El conflicto histórico permanece separado y no se contó
como trabajo sincronizable.
